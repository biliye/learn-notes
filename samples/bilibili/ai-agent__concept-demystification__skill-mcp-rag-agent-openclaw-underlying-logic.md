# 拆穿 Skill/MCP/RAG/Agent/OpenClaw 的底层逻辑：一条"喂上下文 + 调工具"的主线

> 内容整理自 B 站视频《【闪客】一口气拆穿Skill/MCP/RAG/Agent/OpenClaw底层逻辑》（UP：飞天闪客，2026-02-03，约 14 分 46 秒，[原视频](https://www.bilibili.com/video/BV1ojfDBSEPv/)）。证据 = 网页 AI 字幕 445 行 + 44 张关键帧看图，两者相互印证；字幕为 AI 识别，个别专有名词已按画面校正。

## 学完本节你应该获得什么

- 看到一条贯穿全片的主线：所有 AI 新词（Skill / MCP / RAG / Agent / OpenClaw）本质上都是把"意图、环境状态、工具"转成 Token 流喂给大模型，区别只在喂得粗还是喂得精。
- 能背出作者的核心定义：智能体就是"所有不需要智能的部分构成的部分"；这些技术"无非是帮助我们自动往提示词里面增加上下文信息"。
- 能区分几对常被搞混的概念：Function Calling 对应 Agent 与大模型之间，MCP 对应 Agent 与工具服务之间，而 SKILL 是一个"prompt 加载器"。
- 能复述"刚 → 柔 / 稳定 → 变化"的谱系轴：LangChain → Workflow → SKILL → 纯 Agent，知道各自在哪、代表什么倾向。
- 拿到作者与评论区相反的两种立场（Skill 能否取代 MCP），以及关于 RAG 可信度、Token 成本、Agent 权限风险的现实反馈，而不是只信营销话术。

## 一句话总论

这些被吹上天的名词不是新技术，而是同一个东西的不同包装。大模型本身只能"文字接龙"，要靠外层的 Prompt、上下文、记忆、搜索、工具调用这些"不需要智能"的辅助层才变得实用。谁把这些辅助层打包得越顺、越面向普通人，谁就越像智能体。

## 适用场景与前置知识

适用：被 Agent / MCP / Skill / RAG / OpenClaw 概念绕晕、想祛魅搞清底座的人；准备用或正在用 Claude Code、Cursor、Codex、Clawdbot 等智能体产品，但不知道它们各自靠什么跑起来的人。

不适用：想学某个框架（比如 LangChain 的 API）上手写代码的人。本片是概念层，不讲工程落地。

前置知识：知道"大语言模型就是接龙、猜下一个字"即可，不用会写代码。视频里的"小L"= 大语言模型本体，"老板"= 提需求的人或上层应用。

## 知识地图

LLM 大语言模型：只会文字接龙，是唯一的智能来源。

Prompt 提示词：把意图写成它看得懂的话，是唯一的沟通接口。

Context 上下文：喂给大模型的背景信息（需求 + 记忆 + 搜索回填）。

Memory 记忆：把历史对话记录重新塞回上下文，还可再调大模型压缩。

RAG 检索增强生成：用向量库做语义匹配，把外部资料变成上下文；本质也是 search 的一种。

Agent 智能体：夹在老板与大模型之间的"传话筒"，替老板处理大模型做不了的事。

Function Calling：大模型与 Agent 之间"要不要调哪个工具"的约定。

MCP 模型上下文协议：Agent 与外部工具/服务之间的调用约定。

SKILL 技能：一个 prompt 加载器，用 SKILL.md 说明书 + 配套脚本告诉 Agent"这件事怎么做"。

Workflow 工作流：低代码拖拽的多步流程，比 LangChain 更柔一些。

SubAgent 子智能体：独立子任务单独跑，上下文隔离，不保留在主 Agent 中。

Token：计费与上下文的度量单位，作者一句"实在是太贵了"点破当下瓶颈。

## 核心概念卡

LLM 大语言模型（小L）：大模型本身只能做文字接龙，就是不断输出下一个字。以前它是"智障模型"，随着参数大到某个临界点才涌现出智能，为作区分前面加了个"大"字。它本质是一个"把话接着说下去"的东西，不自己做事、不会查资料。

Prompt 提示词与 Context 上下文：把背景信息（Context）和最终指示（Prompt）一起交给大模型。视频用一个"十块钱去天津做一日游"的段子开场：老板给 Context，你拿 Prompt 提问，小L 回答。这里作者埋了个关键伏笔——小L 只能一问一答就结束、不能追问，这个限制决定了后面 Memory 为什么会出现。

Memory 记忆：因为小L 不能追问，你每次沟通前把之前的对话历史放进 Context，伪装成多人对话，再给出新问题；你把这种"特殊的上下文信息"起名叫 Memory，意为大模型的记忆。这些 memory 还可以再次调用大模型进行总结、压缩，从而减少上下文长度。所以它不是存在模型内部的记忆，而是把历史文本当上下文反复灌。

RAG 检索增强生成：你发现的第一个问题是"小L 没有上网查阅资料的能力——要么不知道、要么胡说八道，说的都是过时消息"。于是让大模型说"如果需要上网搜索就告诉我"，你查完再喂回给它。对本地文档或数据库则改用向量数据库，把语义相近的片段找出来，这种"语义匹配向量化并加入上下文、以增强生成可靠性"的方法就叫检索增强生成。作者刻意把联网搜索也叫成 search，还说"连 RAG 也算是 search 的一种，都属于获取模型参数以外信息的能力"。

Agent 智能体：早期所谓智能体的实现逻辑，其实仅仅是多加了一段 prompt（比如"你是李白"或老板设定），从今天的视角回看就是诈骗。真正意义上，Agent 是夹在老板与小L之间的一层程序，用来减少你与大模型直接沟通的次数、处理小L 无法直接操作的事（搜索、调工具）。作者概括得极准：智能体就是所有不需要智能的部分构成的部分——凡能用固定程序解决、不必问大模型的地方，就是 Agent 发挥作用的区域。

Function Calling：你希望大模型按指定的死板格式（比如 JSON）回复"要调哪个工具、参数是什么"，程序才好解析。这个 Agent 与大模型之间关于工具调用所约定的对话格式，就叫 Function Calling。作者说得很直白：其实就是个约定罢了，就好像开发时前端和后端约定这个接口格式一样。

MCP 模型上下文协议：右边那些工具（搜索、文件读取、脚本执行、PDF 转换）要能独立成服务，就得有一套"程序如何发现并调用它"的规范——比如约定 tools/list 方法返回工具列表、tools/call 方法调用具体工具。这套约定就是 MCP，翻译过来叫模型上下文协议。作者一句话刻画三者：大模型就像个只会说话不会做的智者，MCP 服务是能提供各种工具的程序集，中间的 Agent 就是个传话筒。

SKILL 技能：当 PDF / Word / TXT / PPT 输入、HTML / PDF / 图片输出的组合多到不想写 N 套工作流、又不想丢掉"用自然语言触发"的体验时，做法是准备一个目录，把所有可能用到的转换脚本都写好，再写一个统一说明文件描述整体流程，让 Agent 按文件格式灵活选脚本；之后干脆把这句"先读说明再执行"固化成程序，从约定好的位置读 SKILL.md。本质上它就是一个 prompt 加载器，唯一硬性文件是 SKILL.md，其他不做要求。它把"怎么做好某类事"的解释成本，从每次重复描述变成一次性写到文档里、按需读取。

Workflow 工作流：为了让"提取 PDF → 翻译 → 保存成 Markdown"这种相对稳定的流程不靠 Agent 自由发挥（既不稳定又费 token），你可以编程固化或用 LangChain 排链；为照顾非程序员，又发明了低代码拖拽的方式，叫 Workflow。它是把程序替换成低代码拖拽，改写起来相对容易一些。

SubAgent 子智能体：复杂任务会让 Agent 的上下文过大，于是对独立的子任务开一个子 Agent 单独完成。本质上就是做了上下文隔离，子 Agent 产生的上下文不会保留在主 Agent 的中。

## 方法与流程：Agent 究竟怎么跑

把全片散落的图拼成一条可复用链路。

第一步，人描述需求，比如"帮我整理下今天最劲爆的新闻"。Agent 对你的输入不做任何改造，原封不动送给大模型。

第二步，大模型做判断，基于系统提示词决定是直接回答，还是需要调用工具。

第三步，需要调用工具时就进入 Function Calling：大模型按约定的 JSON 格式返回 call_id、name、arguments，比如"调用 search，参数是劲爆新闻"。

第四步，Agent 决定实现路径：加载 SKILL 还是走 MCP。SKILL 提供"怎么做"，是本地手册加脚本；MCP 提供"连哪个外部或远程服务"。

第五步，MCP 连外部服务：需要联网、实时数据、第三方服务时，经 tools/list 和 tools/call 去调，比如搜索、文件读取、脚本执行、PDF 转换。

第六步，回填上下文再循环：工具结果塞回上下文（RAG 和 search 都是把外部资料变上下文的一种），喂给大模型继续推理，直到不需要工具，给出最终答案。

选型谱系轴（刚 → 柔 / 稳定 → 变化）：LangChain 是纯编程、硬编码，最稳定但失去柔性、难包容小问题；Workflow 把程序换成低代码拖拽，改写容易些；SKILL 把"由程序控制的流程"变成"由智能体自行控制"，但提前写好说明文档和可运行脚本，既留灵活调整空间又不至于不可控；纯 Agent 最柔，可随时按判断调整流程，甚至自己给自己生成一个脚本来运行，但这也意味着容易失控，你不知道它中间会写什么脚本。

作者给的核心公式：把"模糊的分流逻辑"交给大模型，用语义识别用户想做 A 还是 B；把"确定的分流逻辑"交给程序，比如 PDF 提取文本这个动作。整个体系的目标就是节省人力、降低使用门槛。

## 关键洞察

作者一针见血：所有的这些技术，最终还是离不开大模型和我们之间的提示词。这些技术无非是帮助我们自动往提示词里面增加上下文信息——比如 search、RAG、skill，都是把一堆内容塞进上下文，或通过代理的形式减少和上下文沟通的次数。

名词是中间产物：作者认为这些概念"说得不好听就是拉垮，说得动听是技术发展的中间产物"。SKILL 的"渐进式披露、按需加载"只是特性，等 token 越来越便宜会变鸡肋；特别常用通用的小工具，未来会直接内化进 Agent 主程序，让 SKILL 也偏鸡肋。

判断留一个争议：作者认为 SKILL 可以把 MCP 服务里的工具统统放进 skill 目录并在 SKILL.md 里说明怎么用，因此 SKILL 能取代 MCP；同时认为"MCP 能不能取代 Function Calling"是无稽之谈，这俩完全不搭尬。但评论区有明确反驳：MCP 的核心价值是远程服务调用，更像 AI 的 RPC，与本地封装的 SKILL 不是一个维度。当两种立场对立时，定位你自己的场景（本地封装还是连远程服务）最重要。

对未来的预判：凡是提供便利的方向就是趋势。未来一定有一个打包好的"超级 Agent"，配置好了所有常用的 MCP、SKILL，甚至都不叫这些名字，普通人啥都不用配置直接能用。

Token 是当下最大的瓶颈：越强大、自己默默处理问题的 Agent 背后，消耗的 token 越大。作者说"现在还有个最大的问题，就是 token 实在是太贵了"，但他认为未来 token 会越来越便宜，甚至到能本地部署大模型时，token 就相当于免费。

## 坑点与反例

把 Skill 和 MCP 混为一谈，作者与评论区正好相反：作者说它们不是一个维度、Skill 能取代 MCP；评论区却说"概念多了之后不梳理清楚很容易把 Skill 和 MCP 搞混，边界感越清晰踩的坑越少"，并反驳"Skill 无法取代 MCP，MCP 是远程服务调用/RPC"。别只信一边，先判断你的任务是要"本地封装"还是"连远程服务"。

把 Function Calling 和 MCP 混为一谈：作者重点澄清——一个是 Agent 和大模型沟通的约定（让大模型回答符合格式、方便解析），一个是 Agent 和工具服务之间调用的约定（像接口文档定传参和返回值），完全不搭尬；"MCP 能否取代 Function Calling"更是无稽之谈。

RAG 被高估：评论区普遍认为 RAG 名字取得最高级，但实际上是整个流程里最不靠谱的一环；基于词向量加重排的 RAG 几乎无法真正实用，有人干脆拿它当反向召回剔除不相关内容。百度、谷歌搜索本质上也是 RAG。

Token 成本被忽视：能力边界扩展是靠更高权限加暴力枚举换来的，评论说得直白，"token 烧的比流水都快"。

Agent 的安全隐患：Clawdbot 这类产品权限太高、错误率太高，有真实的数据不敢给它，不给又看不出用途，这个痛点不解决，AI 很难飞入寻常百姓家。

自然语言编程的落地难：想法美好、工程可行，但受限于大模型的幻觉，考验开发者的组织、编排、错误处理与回退能力。

名词诈骗的营销本质：高情商叫"中间产物"，低情商就是"名词诈骗"。有评论调侃，在程序里嵌几个 prompt 文件和工具，哪有 MCP、skill 好听，本质是给客户和投资讲故事。

## 实践清单

拿一个你正在用的 AI 工具（Claude Code、Cursor、Clawdbot），说清它背后靠哪几层：是大模型加提示词加上下文，要不要检索，要不要调外部工具。

判断"它如何知道实时信息"，是 RAG 或搜索，还是靠 MCP 接的某个服务。

打开它的 skills 目录，读一个 SKILL.md，看 front-matter（name、description）和步骤说明怎么写，体会上下文隔离与按需加载。

把一件重复性任务封装成 Skill，而不是每次重复描述，体会它省 token、不污染主上下文。

使用任何高权限 Agent 前，先想清楚哪些数据我敢给它、有没有审计或沙箱，这是评论区反复强调的落地红线。

## 自测题

Memory 记忆是存在模型内部，还是把历史对话重新塞回上下文？答案：后者，因为小L 不能追问，只能把对话历史放回 Context，伪装成多人对话。

大模型的能力天花板是什么？答案：只会文字接龙，其余都要靠外层辅助层补。

为什么需要 RAG？答案：小L 没有上网和查库能力，只能答过时消息；RAG 本质也是 search 的一种。

Function Calling 的本质是什么？答案：Agent 与大模型之间关于工具调用的约定，让大模型按 JSON 死板格式回，就像前后端约定接口格式。

MCP 和 Function Calling 的分工？答案：前者是 Agent 与工具服务的调用约定，后者是大模型与 Agent 的沟通约定，二者不搭尬。

Skill 的核心组成与本质？答案：核心是 SKILL.md，本质是 prompt 加载器，配套脚本可选。

刚柔谱系轴怎么排？答案：LangChain 到 Workflow 到 SKILL 到纯 Agent，纯 Agent 可自生成脚本但易失控。

作者怎么定义智能体？答案：智能体就是所有不需要智能的部分构成的部分，能程序解决的不问大模型，模糊分流才交给大模型。

作者与评论区对"Skill 能否取代 MCP"的分歧？答案：作者认为可以（工具塞进 skill 目录即可），评论区认为不可（MCP 是远程服务调用/RPC）。

这些技术的终极本质与瓶颈？答案：本质是自动往提示词里塞上下文信息，瓶颈是 token 太贵，但趋势是变便宜、靠便利胜出。
